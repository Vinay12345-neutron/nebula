## Executive Summary & Feasibility Classification

### **Feasibility Classification: B. POSSIBLE with a small native wrapper/runner**

**Rationale**:
1. **Upstream CXLMemSim API Structure**: CXLMemSim does **not** provide a high-level bulk DMA or streaming transfer API in Python. Its native C++ classes (`CXLController`, `CXLMemExpander`, `CXLSwitch`) accept either individual 64-byte transaction events or a vector of cache-line accesses (`std::vector<std::tuple<uint64_t, uint64_t>>`).
2. **Impracticability of Direct Python Instantiation**: For an expert transfer of $256\text{ MiB}$ ($4,194,304$ cache lines), materializing $4.2\text{ million}$ Python tuple objects per transfer across $75,546$ evaluations would require petabytes of object churn and hundreds of hours of Python runtime.
3. **Feasibility via Native C++ Runner**: CXLMemSim's native C++ architecture can evaluate millions of 64-byte transactions in milliseconds when executed compiled in C++20. A lightweight standalone native C++ runner (`cxlmemsim_runner`) that ingests a compact transfer descriptor trace generated by TierMoE Python, expands the concurrent transfers into genuine CXLMemSim cache-line streams, and executes them against real `CXLController` and `CXLMemExpander` instances is completely feasible **without modifying upstream CXLMemSim**.

## 1. CXLMemSim Architecture Relevant to EXP-05B

CXLMemSim (`~/Vinay/CXLMemSim`) is a trace-driven and hardware-assisted CXL memory-system simulator designed to model Type-3 CXL Memory Expanders and CXL switching fabrics. 

The architecture contains three primary operational layers:

```
+-------------------------------------------------------------------------------+
|                             Client / Workload Layer                           |
|      (PEBS/LBR hardware monitors in legacy mode; OR offline trace/runner)     |
+-------------------------------------------------------------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                       CXLController & CXLSwitch Fabric                        |
|  - Manages topology tree (Newick format, e.g. "(1);" or "(1,(2,3));")          |
|  - Routes requests via HDM Decoder / Address Maps                             |
|  - Aggregates fabric bandwidth contention and congestion penalties             |
+-------------------------------------------------------------------------------+
                                      |
                                      v
+-------------------------------------------------------------------------------+
|                           CXLMemExpander (Endpoint)                           |
|  - Queue Management: request_queue_ (capacity 64)                             |
|  - Flow Control: read_credits_ (default 2), write_credits_ (default 2)        |
|  - In-Flight Pipeline: in_flight_requests_ (address -> CXLRequest)            |
|  - Pipeline Stages: frontend (10ns) + forward (15ns) + mem (300ns)            |
|                     + resp (20ns) + flit overhead (6.5ns) + congestion delay  |
|  - Bandwidth Saturation Model: piecewise non-linear MLC queue penalty curve   |
+-------------------------------------------------------------------------------+
```

For Project TierMoE, the relevant subsystem is the **offline trace-driven memory-system simulator** composed of `CXLController`, `CXLSwitch`, `CXLMemExpander`, and `BandwidthModelConfig`.

### G. Can multiple requests be outstanding concurrently?
- **Source**: [`include/cxlendpoint.h:415-420`](file:///home/k8s-admin/Vinay/CXLMemSim/include/cxlendpoint.h#L415-L420), [`src/cxlendpoint.cpp:812`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L812).

- **Yes.** The controller tracks concurrent threads/streams via `thread_map[tid]`, where each stream has its own ROB state and thread info.

### I. How is stream/client identity represented?
- **Source**: [`include/cxlendpoint.h:75`](file:///home/k8s-admin/Vinay/CXLMemSim/include/cxlendpoint.h#L75).
- **Representation**: `uint64_t tid` (Thread ID / Stream ID).

### J. Does the simulator maintain shared queue state across those streams?
- **Source**: [`include/cxlendpoint.h:411-413`](file:///home/k8s-admin/Vinay/CXLMemSim/include/cxlendpoint.h#L411-L413).
- **Yes.** In `CXLMemExpander`, all requests regardless of stream/thread ID enter `request_queue_` and `in_flight_requests_`, protected by a single shared `queue_mutex_`. In `CXLController`, `lru_cache` and `occupation` are shared across all streams.

### K. How does a request move through the simulated pipeline?
- **Source**: [`src/cxlendpoint.cpp:768-794`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L768-L794), [`src/cxlendpoint.cpp:796-828`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L796-L828).
- **Stages**:
  1. `frontend_latency_`: 10.0 ns
  2. `forward_latency_`: 15.0 ns
  3. Memory access: `latency.read` (e.g. 300.0 ns)
  4. `response_latency_`: 20.0 ns
  5. `calculate_protocol_overhead(64)`: 6.5 ns (flit packing)
  6. `calculate_congestion_delay(timestamp)`: non-linear queue occupancy delay ($0$ to $20+\text{ ns}$)
  7. When issued at `current_time`: `complete_time = current_time + total_pipeline_latency`.

### L. How is request completion detected?
- **Source**: [`src/cxlendpoint.cpp:801-808`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L801-L808).
- When `process_queued_requests(current_time)` is invoked, requests with `complete_time <= current_time` are retired from `in_flight_requests_`, and credits are released.

### M. Where is the completion timestamp stored/returned?
- **Source**: [`include/cxlendpoint.h:79`](file:///home/k8s-admin/Vinay/CXLMemSim/include/cxlendpoint.h#L79).
- Stored in `CXLRequest.complete_time`.

### N. Can we retrieve per-request latency?
- **Yes.** Per-request latency is `complete_time - issue_time` or directly computed via `calculate_pipeline_latency(req)`.

### O. Can we retrieve aggregate completion time / makespan?
- **Source**: [`src/main.cc:581-583`](file:///home/k8s-admin/Vinay/CXLMemSim/src/main.cc#L581-L583), [`src/cxlcontroller.cpp:465-466`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlcontroller.cpp#L465-L466).
- `CXLController` does not have a single built-in `get_makespan()` function. Makespan is determined either by:
  a) The latest `complete_time` among all submitted requests in the queue; OR
  b) The transmission span plus `calculate_bandwidth()` contention penalty plus pipeline latency.

### P. Does CXLMemSim model link serialization internally?
- **Source**: [`src/cxlendpoint.cpp:52-92`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L52-L92), [`src/cxlendpoint.cpp:812-828`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L812-L828).
- **Yes.** In the bandwidth model, inter-arrival rates exceeding link peak bandwidth drive link utilization above 100%, triggering queue penalties. In the queue model, requests wait in `request_queue_` until credits become available.

### Q. Does it model queue contention internally?
- **Source**: [`src/cxlendpoint.cpp:830-842`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L830-L842).
- **Yes.** `calculate_congestion_delay()` introduces delays: 0 ns if queue utilization $< 50\%$, up to 20 ns if $< 80\%$, and steep increases up to 100 ns as the queue nears capacity.

### R. Does it model memory-controller contention internally?
- **Yes.** Contention in the endpoint controller queue and the shared MLC bandwidth saturation curve directly model memory-controller buffer occupancy.

### S. Does it model multiple outstanding requests / MLP?
- **Source**: [`src/cxlendpoint.cpp:163-170`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L163-L170).
- **Yes.** If requests arrive within $< 100\text{ ns}$ of each other, `calculate_latency()` applies a pipeline overlap discount:
  $$\text{overlap\_ratio} = 1.0 - \frac{\Delta t}{100.0}$$
  $$\text{overlap\_benefit} = \text{current\_latency} \times \text{overlap\_ratio} \times 0.5$$

### T. Does it require materializing every 64-byte request individually?
- In the queue interface (`insert()`): **Yes**, each 64-byte request must be submitted.
- In the access vector interface (`calculate_latency`/`calculate_bandwidth`): **Yes**, each element in `std::vector<std::tuple<uint64_t, uint64_t>>` represents a single 64-byte line.

### U. If we submit 4,194,304 requests for one 256-MiB expert, what is the expected computational/memory cost?
- **Memory**: $4,194,304 \times 16\text{ bytes} = \mathbf{67.1\text{ MiB}}$ RAM per expert block.
- **Computation**: In native C++, iterating through 4.19 million tuples and executing arithmetic takes **$\approx 15 - 25\text{ ms}$** per expert block. Across 75,546 transfers, native vector evaluation requires $\approx 25\text{ minutes}$.
- In Python, creating 4.19 million objects per transfer would crash memory or take hundreds of hours.

### V. Is there an existing bulk/stream API that avoids materializing 4.2 million Python objects?
- **No.** CXLMemSim has no bulk streaming API in its headers. A native C++ runner is required to bridge the gap.

### W. Can a 256-MiB sequential read stream be represented compactly?
- **Yes.** A compact descriptor: `{batch_step, stream_id, expert_id, base_addr, 268435456, start_time_ns}` can be read by a native C++ runner, which expands it into cache lines internally.

### X. Can several such streams be submitted concurrently?
- **Yes.** When $K$ streams are active at a batch step, the native runner can interleave their cache lines across the link (round-robin or chunked) and feed them to the same `CXLController`.

### Y. Is the simulator event-driven, cycle-driven, timestamp-driven, or another mechanism?
- CXLMemSim is **timestamp-driven and analytical queue-driven**. It is not a cycle-accurate hardware simulator like gem5 or DRAMSim3.

## 3. Concurrency & Timestamp Semantics

### What CXLMemSim Does When Multiple Streams Issue Requests at Time $t = 0$:

1. **Link Bandwidth & Utilization**:
   If Stream 1 ($256\text{ MiB}$) and Stream 2 ($256\text{ MiB}$) start simultaneously at $t = 0$:
   - The combined instantaneous injection rate doubles.
   - For link bandwidth $32\text{ GB/s}$, the combined traffic requires serialization across the shared physical link.
   - In `CXLSwitch::calculate_bandwidth()` ([`src/cxlendpoint.cpp:439-473`](file:///home/k8s-admin/Vinay/CXLMemSim/src/cxlendpoint.cpp#L439-L473)), all accesses in the window $[0, T]$ from all streams are aggregated:
     $$\text{observed\_gbps} = \frac{(N_1 + N_2) \times 64}{\max(T, 100000)}$$
   - If the requests are issued without serialization spacing, observed bandwidth spikes to infinity, pushing utilization beyond $98\%$ and triggering the maximum saturation penalty.
   - Therefore, concurrent streams must be **interleaved across the shared physical link** at link transmission granularity ($\Delta t = 64 / \text{BW}$ per line).

2. **Memory Controller Queue Contention**:
   When multiple streams contend, `request_queue_` depth increases, triggering `calculate_congestion_delay()` to add queuing delays to all active streams.

### Native Runner Implementation Structure (`cxlmemsim_runner.cpp`)

```cpp
#include "cxlcontroller.h"
#include "cxlendpoint.h"
#include <iostream>
#include <vector>
#include <fstream>

struct BatchTransferBatch {
    int step_idx;
    std::string algo_key;
    int batch_size;
    std::vector<uint64_t> expert_base_addrs;
};

// For each batch step with K transfers:
void simulate_batch_step(CXLController* ctrl, CXLMemExpander* ep, const BatchTransferBatch& batch, double bw_gbps) {
    size_t K = batch.expert_base_addrs.size();
    if (K == 0) return;

    // Total cache lines across all K contending transfers
    size_t lines_per_expert = 4194304;
    size_t total_lines = K * lines_per_expert;
    double inter_arrival_ns = 64.0 / bw_gbps;

    // Interleave stream cache lines into shared access vector
    std::vector<std::tuple<uint64_t, uint64_t>> accesses;
    accesses.reserve(total_lines);

    uint64_t current_ts = 0;
    for (size_t line = 0; line < lines_per_expert; ++line) {
        for (size_t stream = 0; stream < K; ++stream) {
            uint64_t addr = batch.expert_base_addrs[stream] + line * 64;
            accesses.emplace_back(current_ts, addr);
            current_ts += inter_arrival_ns;
        }
    }

    // Call genuine CXLMemSim controller functions
    double penalty_ns = ctrl->calculate_bandwidth(accesses);
    double avg_lat_ns = ctrl->calculate_latency(accesses, 110.0);

    // Total makespan: serialized transmission + CXLMemSim-modeled queue & link contention
    double makespan_ns = current_ts + penalty_ns + avg_lat_ns;
    // Record step results...
}
```
